Run your own autonomous AI company

A fully autonomous, 24/7 AI company you stand up on your own Hetzner server with Coolify. One container: a cockpit dashboard + a self-driving loop of 14 expert-persona agents that find demand, build, deploy, and sell — steered only by short human directives.

01 What you're receiving

One Docker container, built from the repo's Dockerfile, running two processes. State lives on three persistent volumes; you steer via a human directive.

Coolify (your instance) → builds Dockerfile → runs 1 container tini (pid1) → docker-entrypoint.sh ├─ python3 dashboard/server.py cockpit :8787 └─ scripts/core/auto-loop.sh the loop (Claude · Codex fallback) volumes: /app/memories /app/projects /app/logs MCP: context7 + airtable + linear (your API keys)

04 The required minimum to boot

Three env vars and it runs — everything else is optional and can be added later:

  • CLAUDE_CODE_OAUTH_TOKEN — from claude setup-token (headless Claude auth)
  • GH_TOKEN — a GitHub PAT for the company's own commits/deploys (a separate identity, ideally)
  • COMPANY_GIT_NAME / COMPANY_GIT_EMAIL — the company's git author

05 How you steer it

You never micromanage — you write a human directive, and the loop treats it as top priority for the next cycle, then marks it done. Two ways:

  • Cockpit — Director panel → click a template button (Hold+Discover · Discovery · Un-hold+Validate · Select+Validate) → paste → fill <FILL> → Send.
  • CLI — apply-directive.sh writes the directive into the live container and confirms it registered.

Each template carries a Blocked / Pending Work register — so the company always knows what's parked (e.g. a payment link in KYC) and why, and keeps discovering opportunities meanwhile.

07 Troubleshooting — cockpit looks primitive / behind

Symptom: the dashboard shows only Guardian / Daemon / Loop / Runtime State, reads Loop: STOPPED or "read-only dashboard", and is missing the Director, Settings, Opportunity Analyst, Cost, and Ideas panels.

Two causes — both must be fixed: (1) the deploy is on old code, not the latest main; (2) the loop isn't running — no real container / no secrets, so every panel is empty.

  1. Deploy from the latest main — Coolify → app → Configuration → Git Source → Branch = main → Save → Redeploy. Build pack = Dockerfile (a real container, not a static / read-only build).Restores the full modern cockpit: Director (+ template buttons), Settings, Analyst, Cost, Ideas.
  2. Run the real container with secrets — port 8787, the three volumes, and at minimum CLAUDE_CODE_OAUTH_TOKEN + GH_TOKEN + COMPANY_GIT_NAME/EMAIL (full list: logs/runtime.env.example).Starts the loop so the panels fill with live data.

Verify: the Director panel + template buttons appear, Loop: RUNNING, the cycle count climbs, Consensus Head updates, GET /api/status → 200. Integrations (Context7 / Airtable / Linear) can be added later — MCP servers fail open, so a missing key never crashes the loop.

08 Troubleshooting — cockpit is live but the loop won't start

Symptom: the modern cockpit renders (Director, Settings, Analyst, Cost, Ideas all present) and GET /api/status → 200, but no cycles run. The entrypoint hard-stops when CLAUDE_CODE_OAUTH_TOKEN is absent — that is correct; never bypass it with a dummy value.

Cause: the four boot secrets aren't in runtime.env yet. Two are personal credentials — each instance brings its own; do not reuse another operator's tokens (billing + security).

CLAUDE_CODE_OAUTH_TOKENRun claude setup-token on your own machine (logged into your Claude Max/Pro). Runs the engine on your subscription. secret
GH_TOKENGitHub → Developer settings → PAT (classic), repo scope, your account — the loop pushes to your fork. secret
COMPANY_GIT_NAMECommit author name, e.g. Auto Company.
COMPANY_GIT_EMAILCommit author email, e.g. bot@yourdomain.
  1. Write them without echoing the values — literal KEY=value, one per line, no quotes (GH_TOKEN=ghp_xxx, never "ghp_xxx"), no trailing space/CRLF. The entrypoint parses this file literally — it never dot-sources it. umask 077 first; append the two non-secrets with a heredoc; pipe each secret in via read -rs -p "…: " T && printf 'KEY=%s\n' "$T" >> $F; unset T so nothing lands in shell history.
  2. Start the full loop — run the prepared start-full.sh. It prints only the names of any still-missing keys and stops; once all four are present it launches the same image via docker-entrypoint.sh and the loop begins.Verify: docker logs -f <container> | grep -E "Cycle #|\[OK\]" — the first Cycle #1 … [OK] means the loop is live and the panels start filling.

Not a bug: curl -I (HEAD) returns 501 because the Python server implements only GET; use GET /api/status for health checks. Binding to 172.17.0.1:8787 (not public 0.0.0.0) is correct — the cockpit stays behind your reverse proxy. Codex fallback is optional; the loop runs on Claude alone.

🪟 Windows operators — where the Claude token lives

The token is not stored on Windows — Windows is only where you generate it. It lives in one place: the server's runtime.env. The loop runs in a Linux container; Windows just produces the string.

  1. Generate on Windows — in PowerShell / Windows Terminal run claude setup-token (needs Claude Code CLI: npm i -g @anthropic-ai/claude-code, or run it from WSL / Git Bash). A browser opens → sign in with your Claude Max/Pro → the token prints to the console. Copy it.
  2. Paste into the server, not a Windows file — SSH into the host and run the read -rs line on the Linux side, then paste. This avoids the #1 Windows trap.CRLF: never author runtime.env in Notepad / a Windows editor — \r\n endings make the parser read token\r and auth fails. Pasting into the server shell (or editing with nano on the host) keeps it clean. No quotes around the value.

No backup needed — the token is regenerable: lose it, re-run claude setup-token and update the one line. If you must keep a copy, use Windows Credential Manager, not a plaintext file.

🔁 Optional — connect the Codex fallback

Codex is not required — the loop runs on Claude alone. It's a second engine the router fails over to when Claude hits its usage limit or the budget cap. Wire it only if you want that resilience. It's a one-time seed, not a per-deploy step.

  1. Produce an auth.json on your own machine: npm i -g @openai/codex@0.144.6 then codex login (sign in with your ChatGPT Plus/Pro) → writes ~/.codex/auth.json. Rock-solid 24/7 alternative: put an OPENAI_API_KEY in auth.json instead — pay-per-use, never expires. The ChatGPT-sub path is cheaper but can need an occasional re-login.
  2. base64 it → seed CODEX_AUTH_B64 in runtime.env: base64 -w0 ~/.codex/auth.json (macOS: base64 … | tr -d '\n'), paste via the same read -rs line. Restart → entrypoint decodes it to CODEX_HOME=/app/logs/.codex (on the persistent volume) and auto-sets FALLBACK_ENGINE=codex.Verify in logs: Codex auth: seeded from CODEX_AUTH_B64 (first boot), then using persisted …/auth.json on later restarts.

The one trap: seed once, then leave it. During a run Codex rotates its refresh token and writes the new one back to the persisted auth.json. Re-injecting the original CODEX_AUTH_B64 on every deploy resurrects an already-used refresh token → 401 "refresh token was already used". The entrypoint guards this (it never overwrites a persisted auth), so after first boot you can even blank CODEX_AUTH_B64. Also: seed a freshly logged-in auth.json — one more than a few days old is already stale and 401s.

09 Optional — the Opportunity Analyst (Codex 2nd brain) cron

The Opportunity Analyst is an independent Codex (gpt-5.6-sol) that reads the full scan, scores every candidate, challenges the company's own pick, and drafts a paste-ready directive — surfaced in its own cockpit panel with a Copy button. It runs inside the container as user app, but a host cron triggers it. The panel showing LOADED with no content just means the code is present but nothing has run yet.

Prerequisite: the Codex auth from section 08 — the Analyst shares the loop's CODEX_HOME=/app/logs/.codex/auth.json and aborts without it. So the CODEX_AUTH_B64 seed is required for the Analyst too.

Orchestrator scripts/analyst/opportunity-analyst.sh✅ ships in the image (transfers with your fork)
Vendored Codex skill autocompany-opportunity-director✅ ships in the image; the script self-installs it into $CODEX_HOME/skills/ on first run
/api/analysis + Analyst panel✅ ships in the image (the panel you already see)
Host cron opportunity-analyst-cron.sh + /etc/cron.d/…❌ NOT in the repo (host-only, like docker-prune) — you add it yourself for automatic daily runs

Run it once, by hand (after Codex auth is seeded and the loop is up):

C=$(docker ps --format '{{.Names}}' | grep 'auto-company' | head -1)
docker exec -u app "$C" bash /app/scripts/analyst/opportunity-analyst.sh
# ~7–10 min → the Analyst panel fills → Copy directive → paste into Director

For automatic daily runs, add a host cron. Critical: the Analyst and the loop's Codex fallback share one CODEX_HOME — two concurrent codex exec runs cause a 401, so the cron must wait for a codex-idle window before firing.

# /usr/local/bin/opportunity-analyst-cron.sh
#!/usr/bin/env bash
set -uo pipefail
C=$(docker ps --format '{{.Names}}' | grep 'auto-company' | head -1)
[ -z "$C" ] && { echo "no container"; exit 0; }
# wait up to 25 min for a codex-idle window (avoid the loop's codex cycle → 401)
for i in $(seq 1 25); do
  docker exec "$C" sh -lc "ps -eo args | grep -q '[c]odex exec'" || break
  sleep 60
done
docker exec -u app "$C" bash /app/scripts/analyst/opportunity-analyst.sh \
  >> /var/log/opportunity-analyst.log 2>&1

# /etc/cron.d/opportunity-analyst
30 4 * * * root /usr/local/bin/opportunity-analyst-cron.sh

Draft-only by design: the Analyst never applies its own directive — it snapshots/restores human-directive.md so it can't auto-apply. You read it in the panel and paste the ## Directive block into the Director. Registry writes are additive (Archived is never silently deleted).
